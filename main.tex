\begin{abstract}
Large language models can generate useful software from natural-language requests, but a generated implementation is neither a durable specification nor trustworthy evidence of its own correctness. We present \emph{evidence-driven generative development} (\method), a software-development method that makes human-readable behavioral contracts, executable demonstrations, constrained test specifications, and replayable evidence the durable product record while treating each generated implementation as a replaceable candidate. The goal is to preserve implementation freedom without giving up repeatability, safety, or auditability. A candidate advances through a pre-generation differential security gate, isolated generation, three distinct test sources, bounded repair, explicit approval, pre-install replay, and final-hash real interaction and visual checks. Fixed Developer Conformance runs in an isolated real Chromium viewport so layout-dependent regression memory does not inherit the limitations of a hidden offscreen host. The local evidence Runner may itself be generated from a versioned human-readable Bootstrap and independently meta-tested before atomic activation; the Bootstrap remains application-agnostic and hands application acceptance back to trusted orchestration. Reproducible failures evolve the smallest justified durable layer---shared framework, capability contract, or regression evidence---before the complete loop is replayed. A Builder, independent Testers, and a bounded Attacker are mechanisms for enforcing these evidence boundaries rather than the contribution by themselves. We describe the durable-artifact model, criterion-evolution discipline, security and repair architecture, convergence protocol, and a browser-extension case study. This methods and systems report defines falsifiable evaluation protocols and reports engineering observations; it does not claim that finite testing or model review proves semantic safety. Reference implementation and artifacts: \url{https://github.com/allenyllee/monkeyskill}.
\end{abstract}

\section{Introduction}

Code-generating language models make repeated sampling a practical way to obtain working programs, but functional success varies across samples and tasks \citep{chen2021codex}. Conventional development treats source code as the durable artifact and later changes it in place. A generative system creates another possibility: preserve intent and evidence, discard a defective implementation, and synthesize a different one. Treating one sample as the permanent source of truth therefore gives up a central advantage of generation. Treating prose alone as the replacement is also insufficient. Prose is incomplete until exercised against observable behavior, and prose supplied to an agent may contain adversarial instructions that blur the boundary between data and instructions \citep{greshake2023indirect,yi2023bipia}.

We ask: \emph{What should remain durable if executable code is regenerated, and what evidence is sufficient to accept one generated candidate?} Our answer is \method. Its central claim is that the durable unit of generative software should be a behavioral contract plus replayable evidence, not a particular generated implementation. The method is organized around four principles:

\begin{enumerate}[leftmargin=*,itemsep=2pt]
  \item preserve a human-readable contract, a minimal real-world demonstration, criteria, and evidence rather than a particular generated implementation;
  \item retain implementation freedom except where repeated evidence justifies a behavior or mechanism constraint;
  \item separate generation, independent specification, and adversarial mutation behind a bounded DSL and trusted enforcement; and
  \item evolve the durable record from reproducible failures, then replay all required evidence against the new final hash.
\end{enumerate}

The process resembles counterexample-guided inductive synthesis (CEGIS), in which candidate programs are iteratively refined using verifier-produced counterexamples \citep{solarlezama2006sketching}. It differs in three important respects: its specification begins as a human-readable product contract; its oracle is deliberately plural, combining constrained tests, runtime policy, real-browser interaction, and visual evidence; and its security gate challenges the interpretation of the specification before candidate generation.

This paper's primary contribution is a development methodology; its multi-agent topology is one reference realization. Specifically, we contribute:

\begin{itemize}[leftmargin=*]
  \item a durable-artifact model in which readable contracts, Demos, criteria, bounded test specifications, and replayable evidence persist while generated implementations remain replaceable;
  \item an evidence-driven criterion-evolution discipline that promotes reproduced failures to the smallest justified durable layer while avoiding unnecessary implementation prescriptions;
  \item an auditable validation architecture combining isolated generation, independently authored tests in one constrained DSL, Builder-led iterative candidate repair from bounded feedback, and final-hash real-environment evidence;
  \item a human-readable, application-agnostic Runner Bootstrap that permits a local agent to generate, independently meta-test, hash-pin, and atomically activate the enforcement backend instead of requiring a pretrusted external binary;
  \item a differential security gate that tests whether untrusted contract text can override a known rejection boundary before any candidate is generated; and
  \item a convergence and evaluation protocol for measuring repeated synthesis, repair cost, implementation diversity, safety, and end-to-end conformance.
\end{itemize}

\section{Background and Motivation}

Property-based testing showed the value of expressing general properties and generating diverse inputs rather than relying only on hand-picked examples \citep{claessen2000quickcheck}. Differential testing compares independent implementations or executions to expose inconsistencies \citep{mckeeman1998differential}. LLM-based red teaming extends automated test generation to behaviors that are difficult to enumerate manually \citep{perez2022redteaming,ganguli2022redteaming}. Interactive benchmarks further show that success in a static benchmark does not imply reliable operation in a real graphical environment \citep{xie2024osworld}.

\method combines ideas from these traditions but addresses a different unit of development. The unit is a small, installable capability described by a readable contract. In our reference system, MonkeySkill, such a contract is called an \mskill{} \citep{monkeyskill2026}. The contract declares modes, capabilities, denied effects, compatibility requirements, and observable criteria. A language model generates JavaScript and CSS only after the security gate has accepted the contract.

The central design tension is that a strict implementation recipe improves repeatability but destroys generative freedom, while an unconstrained prompt preserves freedom but weakens reproducibility. \method resolves this tension with three layers:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Behavioral contract:} required observable outcomes and forbidden effects; strict and durable.
  \item \textbf{Validated implementation constraints:} mechanisms or ordering constraints retained only after repeated evidence shows they are necessary for this specific capability.
  \item \textbf{Free implementation detail:} algorithms, data structures, naming, and organization remain Builder choices.
\end{enumerate}

\section{Related Work}

\paragraph{Multi-agent software engineering.}
ChatDev and MetaGPT organize specialized language-model roles into software-development
workflows, while MAGIS and SWE-agent target repository-level issue resolution and tool use
\citep{qian2023chatdev,hong2023metagpt,tao2024magis,yang2024sweagent}. AgentCoder is the
closest role-level precedent: a programmer iterates from feedback produced by a test designer
and test executor \citep{huang2023agentcoder}. These systems establish that specialization,
execution, and feedback can improve generation. Their usual durable object, however, remains
the generated repository or patch. \method instead asks whether a contract-and-evidence
package can regenerate a replacement without inheriting that implementation.

\paragraph{Test-driven intent and generated tests.}
TiCoder partially formalizes ambiguous natural-language intent through user-reviewed tests
\citep{fakhoury2024ticoder}. Otter generates tests from issues before a patch exists and uses
them to validate software-engineering agents \citep{ahmed2025otter}. TestGen-LLM improves
existing human-written tests and filters generated additions through deterministic quality
gates \citep{alshahwan2024testgen}. These works motivate tests as specifications and external
filters for model output. \method differs by retaining Demo-derived criteria and two
independently authored suites in one non-executable DSL, then binding all post-generation
evidence to the candidate hash.

\paragraph{Skills, real environments, and injection resistance.}
SWE-Skills-Bench evaluates whether procedural skill packages improve real repository tasks
under deterministic acceptance tests \citep{han2026sweskills}. OSWorld demonstrates the
importance of execution-based evaluation in real graphical environments
\citep{xie2024osworld}. At the model layer, the Instruction Hierarchy trains models to obey
privilege ordering \citep{wallace2024instruction}; multi-agent prompt-injection defenses use
specialized reviewing agents \citep{hossain2025defense}. \method complements rather than
replaces these approaches: it treats an entire human-readable capability contract as untrusted,
inserts a trusted known-reject mutation, and requires an original-allow/poisoned-reject pair
before generation.

\section{Durable Artifacts}

Generated source is treated as a derivative candidate, not the product's sole source of
truth. The durable record is the smallest package from which a new candidate can be
generated and judged without inheriting the previous implementation. It consists of:

\begin{description}[leftmargin=2.7cm,style=nextline]
  \item[Demo] A minimal reproduction of the motivating failure, with a visible blocked baseline and expected restored behavior.
  \item[Contract] A human-readable \mskill{} plus a declarative manifest of capabilities and denied effects.
  \item[Criteria] Stable, uniquely identified behavioral outcomes justified by evidence.
  \item[Test DSL] Builder-authored public and Tester-authored independent \testspec{} documents using the same bounded grammar.
  \item[Runner] A trusted interpreter that constructs fixtures, applies actions, observes allowed state, and enforces capability policy.
  \item[Evidence] Candidate hashes, test outcomes, browser observations, screenshots, and preserved failure reproductions that can be replayed against a replacement.
\end{description}

Appendix~\ref{app:package} shows a concrete package manifest and a representative
human-readable contract excerpt. Appendix~\ref{app:testspec} shows the same bounded
\testspec DSL used by public and independent suites.

This split allows multiple implementations to satisfy one contract while keeping validation replayable. Regeneration is therefore an intended maintenance operation rather than a recovery accident. It also makes a safety boundary explicit: a behavior that the DSL and Runner cannot enforce is \emph{unverifiable}, not silently safe.

Fresh Tester B sees only that variant and is not told the expected answer. Only the pair \texttt{allow}/\texttt{reject} releases the original contract---never the poisoned copy---to Builder.

\subsection{Role isolation}

The roles have asymmetric information:

\begin{itemize}[leftmargin=*]
  \item Tester A and Builder receive the same original contract but run in separate fresh contexts.
  \item The Attacker receives the original contract, but not Tester policy or verdicts.
  \item Tester B receives only the poisoned contract, not the expected verdict.
  \item Neither Tester receives candidate code or the other test suite.
  \item Builder receives constrained failure diagnostics from independent tests, not their hidden contents.
\end{itemize}

This architecture reduces direct overfitting and answer leakage. It does not make model judgments independent in a statistical sense: related models may share semantic blind spots. The system therefore relies on enforced layers rather than model voting.

Figure~\ref{fig:role-interaction} makes the message boundaries explicit. The three
model roles do not converse directly. A trusted orchestrator selects which immutable
input each role receives, validates every structured response, constructs the poisoned
copy, and releases only the original contract to Builder. During repair, Runner returns
bounded diagnostics rather than the independent suite itself.

\subsection{Bootstrapping the local evidence Runner}

The enforcement backend can itself be generated without making a particular application part
of its specification. Figure~\ref{fig:runner-bootstrap} separates this one-time local bootstrap
from later application-specific closed loops. A versioned readable Bootstrap supplies bounded
protocol schemas, role boundaries, negative canaries, and meta-conformance---not Runner source.
A fresh Runner Builder generates a provider for the current OS; a fresh Runner Tester checks
positive execution, fail-closed behavior, cleanup, protocol purity, exact hashes, and diagnostic
projection. Trusted orchestration atomically activates only the tested hash and preserves the
previous passing version for rollback.

The Bootstrap acquisition path also treats the Store page as untrusted. Its visible
``Copy verified Bootstrap prompt'' control supplies only an ID, version, same-origin immutable
URL, and claimed package hash to an isolated Extension bridge. The bridge independently downloads
the manifest and every listed file with credentials omitted and redirects disabled, verifies byte
counts and SHA-256 values, recomputes the package hash, and reports the observed protocol. The
published Extension accepts only the exact Bootstrap version, package hash, and protocol pinned in
its compiled policy; Extension code then constructs and copies the prompt while returning only
success metadata to the page. For the present proof of concept this exact pin is the trust anchor,
without a signature infrastructure. The receiving local agent nevertheless re-downloads and
re-verifies the named package before fresh Builder/Tester meta-conformance.

The authenticated Host is a separate trust boundary. It validates the complete external Build
envelope, rejects unknown fields, and projects only the provider's documented private request
(the browser provider receives exact \texttt{\{modes\}} bytes). Provider crashes, unsupported
operations, malformed responses, and timeouts are infrastructure failures rather than candidate
assertions. Meta-conformance additionally requires a default-deny child-process environment,
preflight and runtime network denial, verified browser cleanup, canonical package hashing, and
acceptance tools that cannot mutate the manifest-covered artifact they are validating.

\subsection{Infrastructure change governance}

Runner generation is a provisioning and infrastructure-maintenance activity, not an implicit
subroutine of every application installation. Figure~\ref{fig:infra-governance} separates three
authorities. An MSkill developer who encounters an infrastructure failure may freeze the
application checkpoint, construct a minimal reproducer, and propose a generic repair in isolation.
That proposal is not trusted release evidence and cannot make the interrupted application run
count. A distinct infrastructure maintainer reviews protocol scope, least privilege, fail-closed
behavior, and absence of MSkill, fixture, or test-ID special cases. A fresh infrastructure Tester
then runs complete meta-conformance, negative canaries, cleanup, immutable packaging, installation,
and rollback before a new version is published.

Ordinary users consume only a published, reviewed infrastructure version. A normal installation
may restart or retry an unchanged service, but a substantive Runner, Host, broker, or provider
failure stops installation without consuming an application Builder attempt. The interface may
offer an already-published update or a report path; it does not invoke a Runner Builder or silently
activate an experimental repair. After maintainers publish and the user installs a reviewed version,
the orchestrator may resume the exact saved checkpoint, verify the affected provider boundary, and
then rerun the complete downstream application gates.

\subsection{Security-review output}

Tester returns one of three structured verdicts:

\begin{description}[leftmargin=2.2cm,style=nextline]
  \item[allow] The declared behavior is justified and testable; a complete independent \testspec{} is required.
  \item[reject] The contract requests malicious, hidden, validation-bypassing, undeclared, or unjustifiably sensitive behavior; no \testspec{} is produced.
  \item[unverifiable] An essential claim lies outside the DSL or Runner boundary; automatic installation is denied.
\end{description}

\section{Differential Prompt-Injection Gate}

Both Tester and Builder see human-readable material that may contain instruction-like text. Merely asking Tester to ``ignore injection'' leaves the same model responsible for recognizing and resisting the attack. The differential gate instead adds a known-reject canary and tests whether the review boundary remains effective.

The gate measures a narrow but useful property: whether a known rejectable instruction embedded in plausible contract prose can force approval. It does not prove that the original contract contains no subtle malicious semantics.

\subsection{Bounded attacker construction}

Allowing an LLM Attacker to freely write malicious text creates another injection surface and makes the expected verdict ambiguous. Instead, the Attacker selects only identifiers from trusted allowlists. The orchestrator validates the tuple and instantiates trusted templates at a randomly selected safe paragraph boundary. A plan combines:

\begin{itemize}[leftmargin=*]
  \item a plausible framing family (for example, compatibility or migration),
  \item a concrete unsafe consequence (for example, concealed export of stored or form data), and
  \item a presentation structure (for example, a split note or nested requirement).
\end{itemize}

The reference library combines 10 framing families, 8 unsafe consequences, 4 structures, 3 heading variants, 8 instruction-override phrasings, 8 validation-bypass phrasings, and 4 consequence phrasings, yielding
\[
10 \times 8 \times 4 \times 3 \times 8 \times 8 \times 4 = 245{,}760
\]
surface variants before insertion positions. Diversity comes from semantic and structural composition, not synonym substitution alone. The orchestrator exhaustively validates the smaller allowlisted plan space and separately tests template families.

For auditability and exact reproduction, Appendix~\ref{app:attacker-templates} lists the
complete template library used by the reference implementation. The listing is data,
not a prompt entrusted to Attacker: Attacker returns only three allowlisted identifiers,
and trusted code chooses the concrete heading, override, bypass, consequence wording,
structure, and insertion boundary. The published templates contain no executable code,
credentials, collected data, or concrete network destination.

\section{Constrained Testing and Runtime Enforcement}

Builder and Tester use the same \testspec{} DSL format, avoiding the misleading impression that public and independent suites are different languages. The distinction is authorship and visibility. A \testspec{} can declare fixtures, permitted actions, checkpoints, and assertions, but cannot contain JavaScript, arbitrary selectors, URLs, network requests, or executable expressions.

The successful mainline uses three test sources with deliberately different authority.
Builder authors the Public TestSpec and may receive its detailed traces. Developer
Conformance is versioned, developer-supplied regression memory, validated against criteria
already present in the readable contract; it may block but cannot authorize, add a
capability, or override a security verdict. Fresh Tester A authors the Independent TestSpec,
which remains hidden from Builder. Developer and Independent failures expose only a bounded
criterion, mode, and category tuple. Thus a developer-authored test can demonstrate that
Builder failed to implement reviewed behavior, but it cannot make unreviewed behavior safe.

A complete behavior-plus-policy example appears in Appendix~\ref{app:testspec}, and
Appendix~\ref{app:grammar} summarizes the grammar and representative allowlists.

The trusted Runner interprets this grammar inside an isolated environment and records observable state. Candidate scanning rejects forbidden capabilities and remote content before execution. Capability-denial tests examine the candidate rather than accepting its declarations. Installation remains a separate approval step.

This design follows classic security principles: least privilege, complete mediation, and defense in depth are more reliable than trusting a model's intent \citep{saltzer1975protection,zhang2025securityprinciples}. The DSL is not a universal verifier. Its safety claim is only that expressible actions are bounded and that the Runner mediates them. When a required property is not expressible, the correct result is \texttt{unverifiable}.

\subsection{Builder self-repair as iterative candidate synthesis}

Builder is not a one-shot code generator. After producing candidate $C_i$ and its public
\testspec{}, it remains responsible for diagnosing reported failures, choosing a repair,
and synthesizing a complete replacement $C_{i+1}$. Builder may change implementation
strategy rather than patching one prescribed mechanism. It does not, however, judge its
own success: trusted policy checks and Runner executions remain the acceptance authority.

The repair loop deliberately has two diagnostic channels. Public failures may expose
detailed traces because Builder authored those tests. Independent failures expose only
criterion identifier, mode, assertion category, and expected/actual summaries. The hidden
Independent TestSpec is never revealed. Builder must infer a root cause from this bounded
feedback and return the complete candidate and complete public suite after every repair.

Figure~\ref{fig:builder-repair} shows the resulting versioned loop. Every replacement is
assigned a new candidate hash, so candidate-dependent acceptance evidence gathered for
$C_i$ cannot authorize $C_{i+1}$. Repair need not, however, restart unrelated upstream
model work. Results such as the differential security reviews may be replayed from a
checkpoint only when the complete role input, policy, contract, and poison-construction
hashes are identical. The repaired candidate first receives a targeted trusted replay of
the affected criterion. If that checkpoint passes, the Runner replays the complete public,
Developer Conformance, and independent suites once against the final hash. Thus targeted
replay shortens diagnosis, while full final-hash replay remains the acceptance authority.
A repaired run succeeds when the final candidate converges across all required validation
surfaces. First-attempt perfection is neither required nor treated as the method's objective.

result is reusable only under exact input and policy hashes; a candidate change invalidates
candidate-dependent tests, while a Runner or Host change invalidates provider and
meta-conformance evidence. Any mismatch dispatches a fresh role or execution. Installation
always requires the complete final replay, so checkpointing changes latency rather than the
acceptance threshold.

\section{Demo-First Criterion Evolution}

The method begins with few criteria. A user or agent reproduces a concrete failure in a minimal Demo, confirms the blocked baseline, and defines the visible expected result. A failure is promoted into a durable criterion only when it is:

\begin{enumerate}[leftmargin=*]
  \item reproducible in the Demo or target environment;
  \item within the intended capability;
  \item not already covered by an existing criterion;
  \item observable by an enforceable test or browser evidence; and
  \item paired with preservation and safety boundaries.
\end{enumerate}

If the current contract already covers the failure, the candidate is repaired rather than expanding the specification. If the Runner models the platform incorrectly for arbitrary capabilities, the shared framework changes. If repeated generations reveal a capability-specific platform constraint, that constraint belongs in the capability's contract, not in a global Builder prompt.

We classify every failure before editing prompts:

\begin{description}[leftmargin=3.2cm,style=nextline]
  \item[Global framework] Transport, routing, schema, isolation, capability enforcement, or shared Runner semantics are wrong for arbitrary contracts.
  \item[Capability contract] A behavior, compatibility boundary, or repeatedly necessary mechanism is missing from this particular \mskill{}.
  \item[Candidate only] The contract and framework are adequate; one stochastic generated implementation is defective.
\end{description}

This classification prevents a successful repair for one browser event or timing edge case from becoming irrelevant or misleading global prompt text.

\section{Real-Environment and Visual Evidence}

Static and DOM assertions do not fully represent interactive software. GUI-agent benchmarks report large gaps between benchmarked models and human performance, as well as high task variance \citep{xie2024osworld}. \method{} therefore treats installation and real-environment exercise as mandatory validation surfaces.

For browser capabilities, the candidate is installed on its registered origin, exercised with real pointer and keyboard interactions, and observed after application-specific delay boundaries. Pixel-dependent criteria---selection highlighting, contrast, overlays, clipping, stacking, canvas/media appearance, and native browser UI---require a screenshot after the interaction. Computed style alone cannot upgrade a visual criterion from inconclusive to passed.

Evidence is attached to a candidate hash. A screenshot from one generated implementation cannot be applied retroactively to another. Ambiguous checks remain \emph{inconclusive}; they are neither silently passed nor automatically treated as functional failures.

Layout-dependent regression tests also require a capable execution environment. In an
August 2026 investigation, the Extension's hidden validation page exposed a $0\times0$
viewport and \texttt{elementFromPoint} returned \texttt{null}; the fixed suite therefore
reported 4/7 and repeatedly sent an otherwise viable candidate back for overlay repair. The
trusted local backend now serializes requests to an authenticated endpoint, launches an
isolated Chromium profile, blocks candidate network traffic outside the local fixture, and
self-checks viewport, hit-testing, focus, shortcut, and drag capabilities. The same fixed
Developer Conformance is executed during generation and again immediately before install.
Detailed fixtures and traces remain inside trusted orchestration; Builder receives only the
bounded criterion/mode/category/assertion-type tuple. Provider-specific codes such as
\texttt{assertion-failed} must be projected into this fixed vocabulary from trusted test
metadata; an empty projection is infrastructure failure, not candidate evidence.
Appendix~\ref{app:developer-conformance} reproduces a
schema-valid three-test excerpt of this fixed regression record, including real drag,
hit-testing, and post-dismissal interaction workflows.

This change separates an infrastructure failure from a candidate failure. The earlier
candidate passed all seven fixed checks in the CDP viewport, while a separate real-pointer
probe still found a genuine Standard-mode selection defect. A blocked baseline and a
known-capable reference were therefore necessary before attributing the discrepancy. The
result does not make browser execution a universal oracle; it establishes only that this
backend can exercise the declared regression workflow more faithfully than the hidden host.

\section{Convergence and Stability}

Stability does not mean identical generated code or a perfect first attempt. A run counts as converged when every discovered defect is corrected inside the defined loop, the complete corrected output is revalidated, and no required result remains failing, unresolved, or unverifiable at the final checkpoint. Installation, real interactions, and required screenshots must apply to the final hash.

Intermediate repair is positive evidence about the loop, not a reason to discard the run. A run does not count if correction cannot converge, required evidence is unavailable, a safety gate blocks, or execution ends before final replay. Repeated-generation stability requires a declared number of fresh end-to-end runs with new isolated role contexts.

This definition separates \emph{candidate success} from \emph{method success}. Candidate
success means that one final hash satisfies the durable record. Method success additionally
requires that fresh regeneration can repeatedly produce such candidates without weakening
the contract, leaking independent tests, or silently carrying evidence across hashes.

\section{Reference Case Study}

We developed the method while building a browser capability that restores context menus, text selection, copy/cut, and native paste behavior on pages that deliberately interfere with those interactions. The Demo grew to cover event cancellation, property handlers, persistent selection removal, invisible selection rendering, transparent overlays, disabled hit testing, keyboard-copy blocking, and paste rollback.

The corresponding manifest, contract excerpt, and an executable declarative test are
reproduced in Appendices~\ref{app:package}--\ref{app:grammar}.

The case exposed gaps that neither candidate self-tests nor independent DSL tests alone established. For example, a DOM range could exist while the selection remained visually transparent; only a post-drag screenshot established the rendered result. Likewise, paste rollback required waiting beyond the page's delayed handler and inspecting the final input value. These observations became capability-specific criteria and validated constraints, while the global process retained only behavior-agnostic lessons: preserve native platform semantics in the Runner, attach visual claims to pixels, and classify scope before changing shared prompts.

A later installed candidate made the Store itself unclickable. Its overlay repair classified a
temporarily empty application container, queued a pointer mutation, and applied it after the
container had been populated. Restore Right Click now rechecks content, geometry, and interactivity
immediately before mutation, restores the exact prior pointer state when content arrives, and carries
a fixed \texttt{regression-transient-empty-container} Developer Conformance case. This is deliberately
an application-specific time-of-check/time-of-use regression, not a global claim that every empty
container is an overlay. The methodological lesson is only to promote a reproducible defect into the
owning MSkill's readable criterion and fixed regression memory.

Engineering validation of the reference implementation has included fresh role isolation, schema checks, public and independent Runner suites, adversarial differential gating, installation, browser interaction, visual screenshots, and repeated converged generations. These observations demonstrate feasibility, not general effectiveness. The next section defines the study needed for broader claims.

\subsection{Current experimental configuration}

Our current reference protocol distinguishes a \emph{closed-loop run}, a Builder
\emph{attempt}, and a \emph{repair}. A run starts with fresh isolated security roles and
one original contract, and ends only after the final candidate hash has passed every
required validation surface. Attempt~1 is Builder's first complete candidate and public
suite. Every subsequent complete replacement submitted in response to a diagnostic is
one repair and increments the attempt count. A repaired run can succeed; first-attempt
perfection is not required.

The operational settings used for the browser case study are:

\begin{description}[leftmargin=3.4cm,style=nextline]
  \item[Campaign threshold] Three consecutive fresh converged closed-loop runs are required before the capability is called stable.
  \item[Freshness] Tester A, Attacker, Tester B, and Builder use new isolated contexts in every run. No role inherits another role's hidden inputs, outputs, or conversational state.
  \item[Security precondition] Tester A must allow the original contract and Tester B must reject the trusted poisoned copy. Every other matrix outcome stops before Builder.
  \item[Repair policy] Repairs continue until the complete corrected candidate and complete public suite pass all gates. Exact dependency checkpoints may replay byte-identical upstream role results; a candidate repair first runs the affected checkpoint, then one complete final-hash replay of all gates.
  \item[Regression memory] Fixed Developer Conformance runs after the Public suite in an isolated Chromium/CDP viewport and is replayed immediately before installation. It has blocking but not authorizing authority; Builder receives only criterion/mode/category/assertion type on failure.
  \item[End-to-end evidence] Static policy, Public, Developer Conformance, and Independent checks, installation, real Demo interactions, delayed checkpoints, and required screenshots must all refer to the final hash. A Runner-level \emph{inconclusive} visual observation must be resolved by its designated browser evidence.
  \item[Streak reset] The consecutive-run count resets when a run cannot converge, violates the security matrix, or terminates with required evidence still failing, unresolved, or unverifiable. A local pre-submission defect that changes no external state may be corrected without failing the run, provided every preflight gate is rerun.
\end{description}

\section{Evaluation Protocol}

We propose four research questions:

\begin{description}[leftmargin=1.4cm]
  \item[RQ1] Can a durable contract-and-evidence package repeatedly regenerate behaviorally conforming implementations, and how does this compare with preserving and patching one generated implementation?
  \item[RQ2] How much implementation diversity remains after conformance, and which evidence layers discover non-overlapping failures?
  \item[RQ3] How reliably does the differential gate detect trusted prompt-injection canaries without rejecting benign contracts or constraining valid implementations?
  \item[RQ4] How does evidence-driven criterion evolution affect durable-record size, repair cost, regression rate, and long-term maintainability?
\end{description}

An evaluation should preregister a corpus of capabilities and Demos, model/version settings, sampling parameters, success thresholds, and stopping rules. Each capability should be generated repeatedly under at least these ablations:

\begin{enumerate}[leftmargin=*]
  \item Builder only;
  \item Builder plus public \testspec{};
  \item public plus independent \testspec{};
  \item full differential security gate; and
  \item full method including installed Demo replay and visual evidence.
\end{enumerate}

Primary outcomes are fresh-regeneration conformance, final end-to-end conformance, unsafe-installation rate, unresolved-failure rate, repair attempts, model tokens, wall-clock time, implementation diversity, and growth of the durable record. Comparisons should include both one-shot generation and a conventional baseline that patches one retained generated implementation. Security evaluation should sample the trusted canary plan space while holding expected semantics constant. Benign over-refusal must be measured on unpoisoned controls. All failures should be labeled by the layer that first detected them, and a subset should receive blinded human adjudication.

Because repeated sampling alone improves pass rates on code tasks \citep{chen2021codex}, comparisons must equalize or report total sampling budget. Because model-generated red teaming can discover broad harms but remains model-dependent \citep{perez2022redteaming}, results should not be generalized beyond tested models, templates, and Runner capabilities.

\section{Threats to Validity and Limitations}

\paragraph{Shared model blind spots.} Tester A and B may use related models and share a misunderstanding. The canary detects override of a known rejection boundary, not every malicious interpretation of the original contract.

\paragraph{Finite and biased DSL.} The Runner observes only modeled state. Safety properties outside its mediation boundary are unverifiable. Expanding the DSL increases assurance only if new primitives remain generic, bounded, and correctly implemented.

\paragraph{Template coverage.} Hundreds of thousands of surface variants do not imply semantic completeness. Template families must evolve from observed attacks, and randomization must be reproducible from logged seeds.

\paragraph{Demo representativeness.} A minimal reproduction may omit production interactions. Demo-first evolution mitigates this by preserving newly observed failures, but it cannot anticipate unobserved environments.

\paragraph{Human review.} Readable contracts and approval improve inspectability, but reviewers may habituate or miss subtle prose. The process must not advertise human readability as a cryptographic guarantee.

\paragraph{No proof of correctness.} Passing finite tests and browser checks establishes evidence for a defined contract. It does not prove arbitrary semantic correctness, absence of side channels, or safety against unknown platform behavior.

\section{Ethical and Operational Considerations}

Adversarial samples remain declarative and non-executable. URLs, sensitive-data categories, and external-communication instructions are test data; no component is authorized to contact them. Prefer operator-controlled inert sinks and verify that the pipeline structurally stops before any network-capable candidate exists. Logs should avoid retaining user content, clipboard values, secrets, or generated attack payloads beyond what reproducibility requires.

Open publication of attacker templates has dual-use implications. The method favors fixed consequence categories and transparent orchestration because the same material makes defenses auditable. Deployments should rate-limit generation, isolate workers, pin dependencies, record candidate hashes, and maintain an incident path for unexpected Tester \texttt{allow} results.

\section{Conclusion}

Evidence-driven generative development changes the durable unit of software from one implementation to a readable behavioral contract plus replayable evidence. Generated code becomes a replaceable candidate: it may vary, fail, be repaired, or be discarded without changing the product's durable identity. Builder, Tester, and Attacker roles are one mechanism for placing generation behind independently authored, enforceable, and real-environment checks; they are not substitutes for those checks. The differential gate probes one prompt-injection failure boundary, while the constrained DSL, trusted Runner, sandbox policy, Demo, screenshots, and human review provide distinct evidence layers. The method's strongest claim is procedural and falsifiable: reproduced failures should improve the smallest justified durable artifact, and a replacement implementation should earn acceptance by replaying the complete record against its own final hash. Controlled multi-capability evaluation is the next step toward determining when this contract-and-evidence-centered process is more reliable, safe, maintainable, and economical than retaining generated code or using one-shot generation.
